# Normal reactivated installation startup health

The six POST_TRADE_REACTIVATED applications start after the predecessor has
stopped. The alert dispatcher may sample the expired predecessor lease before
the new automation worker acquires its first lease. That sample is a real
`WAITING_FOR_LEADER` incident. Delivery preserves it in alert history for
explicit operator review; it must not delay or suppress the producer.

## Ordinary handoff

The normal, same-tool installer remains bound to the request's qualified
candidate commit, image, source-file hashes, configuration and six Compose
process identities. Its `START_REQUESTED` stage may record those six exact,
healthy candidate identities even if one tentative current-generation
`WAITING_FOR_LEADER` incident appeared during startup. This is a factual
process milestone, not an installation verification or authority verdict.
Before recording it, the installer requires every other retained financial,
source, control and publication field to equal preflight, the prior alert and
delivery records to remain byte-equivalent, and all new notification rows to
belong to the sole tentative alert. Unknown alerts, additional incidents,
changed old rows, a negative operational state, or any candidate identity
change refuse. An interrupted `START_REQUESTED` resumes by inspecting already
running candidate processes before its strict predecessor snapshot check.
If all six exact candidate containers are already running but some health
checks are still starting, it waits for those same process identities under
the original cutoff before classifying the incident. A mixed candidate and
predecessor process set, changed configuration label, restarted process, or
health timeout refuses without another Compose start.
If the sole alert is temporarily awaiting delivery, the installer rereads
the exact subject within the original deadline. It never treats an unsettled
alert as an accepted financial snapshot.

At `APPLICATIONS_STARTED`, no-append installations retain the original strict
path. If one tentative alert exists, the installer calls the positive
`reactivated_startup.observe_startup_append` witness against the saved process
identities and unchanged request. It must prove the original lease expired,
the dispatcher sampled that lease within the bounded startup window, the
candidate acquired the next fence, the sole alert was delivered without an
ACK, and the same leader recovered for at least 60 seconds. The installer then
rechecks the exact alert and complete preserved financial state, keeps the
original 230-second cutoff and close margin, proves the current leader and
strict published panel, and rechecks the exact incident and notification
history before verification.
The candidate's 60-second recovery can cross a health cursor poll boundary;
retry of the same positive subject is bounded by that original deadline.
The recorded `verified_at` must precede both the unchanged cutoff and the
panel's validity boundary. This is not authority to trade and the result
remains software-only and `operational_ready=false`.

The normal path uses its existing qualified host and application. The running
installer tree and the source files that implement this exception must equal
the request's qualified candidate checkout and its recorded file digests.
It does not require a separate recovery-host report. The separately journaled expired
verification recovery keeps its independent host-tool requirement when an
append is observed. A release built before this rule cannot gain the new
ordinary acceptance by running a replacement installer: each installer source
file and its candidate image are bound to the request qualification.
