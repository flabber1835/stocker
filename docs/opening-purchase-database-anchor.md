# Purchases on an unanchored database

An Alpaca account with backup history, its initial takeover epoch and no physical database identity needs an operator before it can make purchases. Its normal transport guard already enforces that rule. The opening cycle should report `PURCHASES_REQUIRE_DATABASE_ANCHOR` while those purchases remain. It must still reconcile working or unknown orders and execute independent sales.

The execution callback can report this reason after observing unsent purchases. Only read-only recovery can retire the current cycle. It must first obtain a complete, clean reconciliation for the exact broker account observed within the past 60 seconds, rule out working and unresolved orders, verify the current generation and plan fingerprint, and prove that all remaining actionable trades are buys against a resolved projection. It reads the specific upgrade fence again. Pending entitlements, unavailable opening calculations, fee posting, command refusals, and temporal restore fences retain their existing recovery paths. A retired cycle keeps its reconciliation evidence, the unsent purchases and the specific operator reason. The next session can still prepare a plan and sell.

Neither supported repair can turn this active plan into a valid purchase. Restored-account adoption advances the takeover epoch embedded in the plan and every command. The initial PAPER exception requires a never-traded flat account, disabled automation, an engaged kill switch and no live lease. Re-enabling that account creates a new control generation. These conditions are checked under the execution writer lock. Automation may observe an existing anchor but cannot create one as a side effect of diagnosing this condition. The original order deadlines still apply to every eligible plan.
