# Shared dashboard and notification evidence

The dashboard admits account totals only for the selected Alpaca environment and
the durable owned account in that namespace. The observed broker and account must
match both. Display labels follow the selected environment. A LIVE lifecycle
projection requires the enrolled public signature and exact current control and
account identity. It remains separate from the automation worker's recorded
runtime verdict and retains its own expiry. A dashboard reader never grants
transport authority.

An opening display refresh may reuse the exact retained no-transport proof for
superseded, unfilled BUY stubs. The same proof gates its collection and consumption
through the scheduled waiting boundary at execution time. Current, native-matched,
ambiguous or in-flight commands still require ordinary reconciliation. LIVE
read-only opening observation uses the existing scoped native account, orders and
positions checks under current LIVE READ authority. This receipt is display
evidence only.

Native fill notifications can observe an authenticated exact order before the
local financial count advances, in either mode. Each activity page retains its
broker response completion bound and all existing durable identity, clock and
economic checks. Candidate scheduling is bounded and rotates through all eligible
orders. Existing PAPER receipt identities and payloads remain compatible.

Durable due alerts can be claimed independently from repair of historical alert
deficits. Recovery runs on a separate, paced transaction after dispatch and keeps
the existing durable completion rules. Fill recovery joins exact command identity
and native order identity separately, avoiding a repeated command-table scan per
historical fill while retaining both valid and integrity outcomes. Each pass
reads a bounded primary-key page before joining command ownership. The worker's
temporary scan position advances after the batch commits and wraps on exhaustion.
Late rows behind the cursor, failed rows and command-owner changes are revisited.
Restart begins a new bounded sweep. One immutable fill conflict is reported and
isolated so other fills can recover. An unresolved repair is reported independently
from delivery health and cannot strand queued alerts.

Quiet informational rows, pre-migration sends, and obsolete next-opening notices
close without a provider acceptance timestamp. This reuses the rollback-compatible
terminal queue state and records the suppression reason in the delivery event. The
dispatcher and the enrollment view report actual provider acceptance using the
timestamp. A previous device receipt may finalize a retried alert, while only a
new receipt from that attempt recovers its delivery health. The mode comes from
the exact saved plan; the PAPER idempotency key and
payload convention remain usable. Recheck a plan immediately before every bounded
device request and cap request time and provider retention to the scheduled opening
execution. Completed recipient receipts survive a mid-fanout change.

A verified shadow dependency recovery uses the original warning's immutable
identity and exact delivered device receipts. A separate failed or expired device
cannot suppress recovery for a device with a successful warning receipt. Existing
successor and eligibility rules still apply. Once verified recovery is recorded,
skip further attempts to send that warning to devices with no accepted receipt.

The browser applies its hard request deadline to acknowledgement and notification
setup, including response body decoding. An unconfirmed acknowledgement spends its
view token and recovery requires another current view. Enrollment readiness uses
the configured dispatcher freshness and startup bounds, including healthy standby
senders, and distinguishes an enqueued test from real provider acceptance.
