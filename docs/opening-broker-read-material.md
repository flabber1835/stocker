# Opening broker reads and sealed market data

The private 20-purchase rehearsal on November 27 spent 356 seconds inside the structural part of 436 broker read checks. The grant, rolling shadow and readiness paths repeatedly open the same sealed market-data manifest. Its verifier authenticates every normalized block header and the source and reference evidence. These materials depend on stored data. They can be shared while every input is demonstrably identical.

The automated PAPER execution wrapper may retain the last canonical manifest and its operational binding for its own grant. A fresh read-only PostgreSQL observation identifies the exact visible transaction snapshot, database, role, schema and server incarnation. Under its original publication lock, a reader can also prove that an intervening commit left every relevant source row and its schema unchanged. This uses the existing rolling-data verifier's physical row versions, candidate and block identities and DDL epoch. The verifier brackets the first full read with these observations. A change of subject, an unavailable comparison, expiration of the existing 20-minute verification interval, or a change of process forces a full read. Each reader acquires the normal corpus lock, including when it reuses a result. Each caller receives a detached result. A mutation starts outside this read scope.

The live clock, kill switch, lease, account, rollout, signed certificate, executable source, shadow authority and broker evidence are checked at their existing boundaries. Reuse applies only to sealed database material. The audit check for missing ownership events runs at gateway entry. Every broker operation still requires the current durable account binding and owned state.
