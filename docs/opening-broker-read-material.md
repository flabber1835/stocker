# Opening broker reads and sealed market data

The private 20-purchase rehearsal on November 27 spent 356 seconds inside the structural part of 436 broker read checks. The grant, rolling shadow and readiness paths repeatedly open the same sealed market-data manifest. Its verifier authenticates every normalized block header and the source and reference evidence. These materials depend on stored data. They can be shared while every input is demonstrably identical.

The automated PAPER and LIVE execution wrappers may retain the last canonical manifest and its operational binding for their own grant. A fresh read-only PostgreSQL observation identifies the exact visible transaction snapshot, database, role, schema and server incarnation. Under its original publication lock, a reader can also prove that an intervening commit left every relevant source row and its schema unchanged. This uses the existing rolling-data verifier's physical row versions, candidate and block identities and DDL epoch. The verifier brackets the first full read with these observations. A change of subject, an unavailable comparison, expiration of the existing 20-minute verification interval, or a change of process forces a full read. Each reader acquires the normal corpus lock, including when it reuses a result. Each caller receives a detached result. A mutation starts outside this read scope.

LIVE publishes each automated execution read's signed verdict and any account snapshot through its normal fenced evidence writer. Its grant checks run on a fresh connection whose default remains read-only across the verifier's internal rollbacks. Once the check finishes, its read transaction ends. The same physical session resumes its original transaction mode and commits the snapshot together with the verdict only while the exact control generation and lease still authorize it. A failed fence refuses the operation. The two checks around a broker read each reauthenticate the current publication, signed LIVE permissions and account. The submission authority, settled-funding proof and synchronous check at the native HTTP entry run through the original mutation path.

The live clock, kill switch, lease, account, rollout, signed certificate, executable source, shadow authority and broker evidence are checked at their existing boundaries. Reuse applies only to sealed database material. The audit check for missing ownership events runs at gateway entry. Every broker operation still requires the current durable account binding and owned state.

## Metadata used by the standing certificate

The certificate’s metadata reader needs the candidate and manifest already validated when it pins the current publication. In a private opening rehearsal, one metadata read checked all 852 block headers three times. The dashboard feed row separately checked those headers once while reading the current publication.

Within one metadata read, the pin owner supplies its canonical binding and manifest directly to the reference reader. Use that result only when the original read-only database session sees the same full PostgreSQL snapshot before and after measuring metadata. Keep the comparison proof, source and reference validation, and existing publication lock. A changed observation or a database session that cannot establish identical visibility takes the full verification path. The next call pins and checks the publication again. No trading authority is transferred by this operation.
