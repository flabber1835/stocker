## Correction and bust accounting foundation

Do not change the positive-only production fill journal or flatten a correction
into another fill. Implement an isolated, broker-free execution candidate which
replays immutable typed trade events, retaining account, native activity/event,
order, instrument, side and prior-activity identity. A correction reverses its
exact active predecessor and applies the replacement. A bust reverses its exact
active predecessor without inventing replacement economics. Missing predecessors,
forks, conflicting identities/payloads or already-replaced predecessors refuse.
Exact duplicate replay is idempotent; a repeated identity with changed economics
is an error. Persisted candidate envelopes bind original event bytes/digests and
must revalidate on replay rather than trusting derived totals.

This is a gross trade subledger: fees, withholding, dividends, deposits and
settlement are separate financial activities, not inferred from trade price or
commission. Use bounded exact rational arithmetic with Decimal inputs/outputs;
ambient Decimal precision must not change results. Retain native wire evidence
separately from any locally supplied, explicitly interpreted bust operation.

Production correction refusals, native parser refusals, capability/finality bits,
database schema, configuration and execution permissions remain unchanged. The
candidate is not wired into broker observation, journal writes, sizing or cash
availability until separately accepted provider semantics and durable integration
have been qualified. Source: Alpaca's Activities integration guide,
https://docs.alpaca.markets/us/docs/activity-sse (checked 2026-10-24), describes
native ref-id deduplication and prior-ref correction chains. API access, event
completeness, publication/finality, net cash and actual bust payload behavior
still require provider/account acceptance.
