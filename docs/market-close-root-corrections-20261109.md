## Browser scheduler and heartbeat

The initial HTML chooses a refresh interval and embeds it in the controller.
An initially partial 26-second document can select thirteen seconds. Later
reconciliation updates an eight-second lifetime while keeping that initial
thirteen-second timer and cadence floor. The page expires at nine seconds and
waits until thirteen seconds to request again even with zero network delay.

Own the heartbeat and refresh scheduling in the existing controller. Reconcile
newly accepted document metadata, then update the cadence, due time and next
timer together from that accepted document. Validate any new cadence metadata
and retain the minimum ordinary polling bound, single-flight rule, finite retry
and original foreground-resume limits. An expired short-lived fact cannot earn
a new lifetime or an accelerated financial verification through the browser.

Server DOM replacement must not overwrite the device-owned heartbeat with zero.
Use a monotonic clock for visual elapsed-time progression, anchored to the
accepted document's actual age. Keep server UTC proof boundaries, clock-skew
refusals, background/offline withdrawal and financial authority separate. Late
callbacks display the actual current age directly, without replaying missed
digits. Avoid writing unchanged heartbeat text.

Qualification must use the actual controller and reconciler across long partial
to short current documents, delayed responses, expiry, scrolling and resume.
Changing the server alone does not replace already-running JavaScript; local
acceptance must load the corrected controller on the operator client and make
future controller-version handoff explicit without executing untrusted markup.
Do not use looser proof expiry or suppressed grey styling to hide this bug.

## Account and broker freshness

The independent account/execution collector refreshes durable observations on
its own cadence. A market-data retry wake must neither expire a 17-second-old
account snapshot nor renew the same snapshot until tomorrow after a phase change.
For independently collected account facts, retain the existing ten-minute bound
from the original observation regardless of REFRESH, PREPARE or WAITING_OPEN phase.
Never refresh that anchor from page time or an unrelated scheduler update.
Preserve all stricter reservation, protected-order and callback guards and the
existing execution authority checks. Book/plan and backup clocks keep their
distinct owners. Update the older operator-monitoring policy to match.

The first installed candidate applied this account rule too broadly to the
event-driven broker execution observation. The readiness gate correctly refused
it. [The distinct-producer correction](account-and-execution-observation-clocks.md)
restores that row's existing scheduled execution-obligation clock, with original
saved timestamps, active/journal-hazard caps and no new broker authority.

## Row-clock producer contract

The close collector rejected SNAPSHOT_ROW_CLOCK_INVALID for about 21 minutes.
The concrete producer is the post-close calendar projection: the following
market open is exchange-local, and selecting it as the earlier deadline puts a
non-UTC offset into the signed row. The actual calendar/producer/encoder path
reproduces the captured failure fingerprint. Historical raw rows were not retained.
Producer/financial-reader code accepts aware offsets while the operational wire
requires UTC. Align producer contracts: normalize a known aware instant to UTC
before it becomes a row; reject an unknown/naive instant rather than guessing a
timezone. Audit direct row constructors and reproduce a concrete bad producer
path. Preserve strict signed snapshot validation and original absolute instants.

Add bounded safe row/field/clock-kind diagnostics at the producer validation
boundary so another refusal identifies its source instead of retaining only a
generic digest. Do not serialize credentials, raw SQL, row payloads or arbitrary
exception text. Test nonzero offsets, naive/malformed inputs and absence of any
false current/green verdict. Qualification does not invent the missing historical
row or claim that a speculative normalization proves its identity.

for independently authenticated matching publisher progress. Generic financial
checking is insufficient: preserve source/publication/session identity, original
owner/deadline, current worker and all existing refusal clauses.

When fresh financial/attestation rows replace old rows, recompute dependent feed
and automation presentation from those same coherent inputs in the owned
transaction. Do not leave a red feed row after the same response already carries
qualifying typed progress. Make shared projection logic pure and idempotent,
retaining current-negative precedence; never re-run acquisition, corpus hashes,
financial workers or broker reads as a side effect of HTTP or serialization.
Where progress is currently hidden behind generic financial observation, retain
the authenticated producer-owned progress independently rather than converting
unidentified checking into readiness. New financial observations remain owned by
the existing background verifier.

For this independent explanation, combine the existing authenticated SHADOW
attempt (exact current native subject, runtime, QUEUED/RUNNING, no failure),
current matching publication and its original published job/request/candidate,
fresh worker, finite verifier owner, and following market open. Bound it by the
earliest original job, attempt/work, worker, owner and open deadline. Capture

HTTP consumes it without another database observation or corpus verification.
It may explain only the exact current publication's missing readiness verdict
while financial verification is explicitly checking. It never earns READY,
GO, current portfolio values, or any execution permission. Missing, superseded,
failed, ambiguous or expired evidence leaves the original refusal visible.

## Acquisition deduplication

Six dedup lookups scanned roughly 31 million price rows each. PostgreSQL pulled
the existence test into a global distinct-part enumeration before filtering
small part metadata. This is a query-shape defect; the existing primary key is
already suitable. Preserve component/content/row-count identity, exclusion of
the new part, anti-link protection, pinned-or-exact-count admission, created-at
ordering, and the subsequent byte/manifest verification.

Materialize the small matching metadata shortlist first, then use a correlated
primary-key LIMIT-1 existence proof and the original count guard for those IDs.
Do not weaken integrity checks, invent a parallel cache, add a redundant index,
scan corpus/price history for a readiness probe or alter the execution membrane.
Use real PostgreSQL semantics and a planner regression/falsifier that detects
reintroduction of the global price scan. EXPLAIN cost estimates are not runtime
speed measurements; production verification may inspect the plan without
executing the old expensive query.
