# Warm automation observers

Decision, November 20, 2026, before implementation. Docker's five-second automation health probe repeatedly imports the application and opens its own database connection before checking read-only health. The nonfinancial idle authority observer repeats the same imports and syntax parsing in a fresh spawn for each full thirty-second attestation. Both consumers need fresh verification, but process bootstrap provides no evidence of freshness.

Give the automation supervisor one independently bounded, warm health reader. Docker's existing module command opens a private Unix socket and waits within its original five-second limit for a newly sampled result. Each request uses the canonical health predicate, the exact current supervised holder and a fresh database read. Follow the supervisor's monotonic polling pulse, reject a changed holder, and refuse missing, expired, or unreadable evidence. The socket is owner-only and carries no request data. The supervisor reaps failed or overdue health readers without extending its own watchdog deadline. A healthy observation is never served from a cache. The direct module import and explicit `--direct` diagnostic keep the original read path available.

Keep a single warm spawned process for the nonfinancial idle authority observer. Reuse imported modules and exact-byte pure syntax results, while repeating fresh source-path enumeration, source reads, hashes, package facts, signature and control checks under the original thirty-second attestation and twenty-five-second observer budget. The process opens and closes a separate read-only database connection for each request. It carries no result forward. The fenced foreground revalidates the original subject and owns every verdict write. Missing, late, cancelled, malformed, or obsolete replies cannot publish a PASS. Stop and reap the warm process before calling any financial callback and at worker shutdown. The callback's fresh authority checks remain separate.

Qualify the deployed health command's imports, current result, observer liveness and fail-closed timeout. Check successive idle observations use the same warm process while re-reading local and database facts, and that cancellation and timeout discard the process and the result. Keep the existing lease, kill switch, revocation and opening timing tests.
