# Sentinel GO validation liveness

**Decision record, 2026-08-27.**

## Problem

`sentinel-go-validate.sh` currently performs the expensive multi-image/full-test certification phase before attempting the bounded Sharadar/data preparation that is most likely to fail on volatile NAS state. A valid fail-closed data refusal can therefore be discovered only after a long certification run.

The validator also collapses `SharadarMutationRefused` to the exception type, losing the controlled remediation-critical reason that distinguishes cursor/state problems from source-row authority problems.

## Decision

1. Add a **fail-fast data preparation preflight** before the expensive certification suite.
2. The preflight must use an exact clean-main candidate ordinary Sentinel image built from current `HEAD` and the same feed-binding and WAL-durability boundary as production preparation.
3. If the bounded preparation fails, `sentinel-go-validate.sh` exits immediately and does **not** run the expensive certification suite.
4. The preflight may print the controlled message of `maintenance.SharadarMutationRefused` to the local operator console because those messages are generated by Sentinel and contain source/corpus identifiers, not credentials. Other exception types remain type-only.
5. A successful preflight does not grant deployment authority. The full validator still runs and must independently re-prove its normal gates.
6. No broker credentials are forwarded to the preflight container and no broker mutation is possible.
7. Do not blanket-recover every `SharadarMutationRefused`. Some represent ambiguous vendor/source authority and must remain fail-closed. Recovery classification is a separate change under issue #275.

## Operational effect

```text
clean/current main
    |
    v
runtime selection preflight
    |
    v
build exact ordinary Sentinel candidate (Docker cacheable)
    |
    v
bounded Sharadar/data preparation preflight
    |-- failure -> immediate refusal with actionable reason
    |
    v
full candidate-image + certification suite
    |
    v
existing GO validation and evidence bundle
```

This change is intentionally narrow: it removes wasted certification time before known-bad volatile state without weakening any financial boundary or changing strategy/economic behavior.
